# Правила разработки и доработки конфигураций

Как базовые правила написания кода используются правила от 1С [https://its.1c.ru/db/v8std](https://its.1c.ru/db/v8std) , если они не изменены в этой инструкции

# **1. Общее**

## **1.1. Концепция минимизации «разрушений» типовой конфигурации**

Если модифицируемую типовую конфигурацию предполагается обновлять по мере выпуска новых релизов, то разработчикам следует **всегда помнить об этом** и принимать меры по облегчению обновления. Следует всегда выбирать те способы решения задач, которые обеспечат **более простое обновление конфигурации** в будущем, даже если они несколько сложнее в реализации. Конечно, только при условии, что у более удобного для обновления способа нет серьёзных недостатков в области производительности, понятности кода и т. д.

Все доработки выполняются в расширении (в том числе новые метаданные), если это возможно и не усложняет поддержку системы.

## **1.2. Префиксы**

В регламенте описана работа со следующими префиксами:

1. Префикс номера задачи. В регламенте будет использован **"DT"** 
2. Префикс метаданных. Может отличаться в разных системах и разных расширениях. В регламенте будет использован **"MD"**

# **2. Комментирование изменений в коде:**

Абсолютно все изменения программного кода модулей должны комментироваться. 
Блок строк, подвергшийся изменению, должен быть обрамлён строками-комментариями особого формата.
Старый код не удаляется, а комментируется. 
Принцип формирования этих строк показан на следующем примере:

```
//++ DT-48 
<Сведения о доработке (при необходимости)>
//-- DT-48
```

Где:
- //++ — начало блока
- //-- — конец блока
- DT-48 — номер задачи по трекеру с префиком, ставится как в открывающем комментарии, так и в закрывающем.
- <Сведения о доработке (при необходимости)> — произвольный комментарий, используется при необходимости

Комментарии призваны выделять модификации по сравнению с типовым функционалом. Если разработчик изменяет текст своей собственной модификации через некоторое время в рамках этой же задачи, то такие изменения отдельно не комментируются (и имеющийся внешний комментарий тоже не изменяется). Если разработчик вносит изменения в свой текст, но уже по другой задаче или изменяется код, написанный другим разработчиком, то комментирование следует использовать обязательно.

Обрамляющие комментарии выравниваются по левому краю редактируемого блока кода. Способы использования комментирования изменений продемонстрированы на примерах ниже:

## **2.1 Вставка кода**

*Пример*:

```
Процедура ПриОткрытии()
    Если ЭтоНовый() Тогда
        ЗаполнитьПоляПоУмолчанию();
    КонецЕсли;
    НастроитьЭлементыФормы();
    //++ DT-48
    НастроитьДополнительныеЭлементы();
    //-- DT-48
    УстановитьВидимостьПолей();
КонецПроцедуры
```

## **2.2 Удаление кода**

*Пример*:

```
Процедура ПриОткрытии()
    //++ DT-48
    //Если ЭтоНовый() Тогда
    //    ЗаполнитьПоляПоУмолчанию();
    //КонецЕсли;
    //-- DT-48
    УстановитьВидимостьПолей();
КонецПроцедуры
```

## **2.3 Изменение существующего кода**

При изменении существующего кода сначала обязательно комментируется старый блок, затем пишется новый вариант.

*Пример*:

```
Процедура ПриОткрытии()
    Если ЭтоНовый() Тогда
        //++ DT-48
        //ЗаполнитьПоляПоУмолчанию();
        НастройкаЗаполненияПолей = ПолучитьНастройкуЗаполненияПолей();
        ЗаполнитьПоляПоУмолчаниюРасширенная(НастройкаЗаполненияПолей);
        //-- DT-48
    КонецЕсли;
    НастроитьЭлементыФормы();
    УстановитьВидимостьПолей();
КонецПроцедуры
```

## **2.4 Добавление процедур и функций в модуле**

Для добавляемых процедур и функций, а также для объявления переменных модуля типовых объектов действуют дополнительные правила оформления комментариев:

- Комментируется не блок добавленных процедур в целом, а **каждая** добавленная процедура или функция в **отдельности**.
- Открывающий комментарий идёт на строке, предшествующей заголовку процедуры или функции, а закрывающий комментарий идёт **на той же строке**, где написано «Конец процедуры» или «Конец процедуры», через пробел.
- Комментирование изменений внутри существующих процедур осуществляется по общим правилам.

*Пример*:

```
//++ DT-48
Перем мНастройкаЗаполненияПолей; //-- DT-48
 
//++ DT-48
Процедура ПроверитьДоступностьЗаказа()
    ...
    ...
КонецПроцедуры //-- DT-48

//++ DT-48
Процедура ПроверитьДоступностьРеализации()
    ...
    ...
КонецПроцедуры //-- DT-48
```

Данное правило позволяет легко переносить изменения в модуле в «попроцедурном сравнении» конфигураций.

Если же закрывающий комментарий поставить на следующей строке:

```
//++ DT-48
Процедура ПроверитьДоступностьЗаказа()
    ...
КонецПроцедуры
//-- DT-48
```

То при «попроцедурном сравнении» данный комментарий будет признан описанием следующей по тексту процедуры, которая будет считаться измененной.


## **2.5 Изменение имени или параметров функция и процедур**

При изменении имени, изменении параметров или добавление "Экспорт" к методу, комментарий указывается в начале функции.  
Пример:

```
Процедура ПроверитьДоступностьЗаказа(НовыйПараметр = Ложь) Экспорт
    //++ DT-48
    Добавлен новый необязательный параметр НовыйПараметр 
    Добавлено "Экспорт"
    //-- DT-48    
    ...
КонецПроцедуры
```

# **3. Добавление объектов верхнего уровня**

## **3.1** **Добавление объектов**

Объекты верхнего уровня, создаваемых в конфигурации, должны **снабжаться "префиксами метаданных"**, например:

- MD_НовыйСправочник
- *MD_НовыйРегистрСведений*
- *MD_НовыйДокумент*

Для разных систем и расширений префикс может различаться

Синонимы (видимые пользователю имена) добавленных объектов верхнего уровня должны начинаться с префикса, заключённого в круглые скобки: **(MD)**. В результате эти объекты будут визуально выделяться в списках и сгруппировано располагаться в их начале (что облегчает и тестирование, и использование).

В комментарии создаваемого объекта следует указать **номер задачи**, по аналогии с заголовочным комментарием добавляемого кода, но без знаков «++». Это обеспечит привязку объекта конфигурации к задаче, отыскиваемую глобальным поиском.

*Пример*: Создать справочник «Настройки системы».

*Действия разработчика*: в конфигурации создается следующий справочник:

- Имя: MD_НастройкиСистемы
- Синоним: (MD) Настройки системы
- Комментарий: DT-48

## **3.2** **Наследование типовых объектов в расширение**

Наследуемые объекты не меняют своего имени (**без префикса**).

В комментарии наследуемого объекта следует указать **номер задачи**, по аналогии с заголовочным комментарием добавляемого кода, но без знаков «++». Это обеспечит привязку объекта конфигурации к задаче, отыскиваемую глобальным поиском.

*Пример*: Унаследовать в расширение типовой справочник «Настройки системы».

*Действия разработчика*: в конфигурации наследуется справочник и устанавливается:

- Комментарий: DT-48

# **4. Добавление подчиненных объектов**

## **4.1** **Добавление подчиненных объектов в типовые объекты**

Добавляемые подчиненные объекты в типовые объекты, должны **снабжаться "префиксами метаданных"**:

- *MD_ДополнительныйРеквизит*,
- *MD_НоваяТабличнаяЧасть*,
- *MD_ФормаНастроекПользователя*,
- *MD_МакетСпециальнаяНакладная*.

Но при этом синонимы таких подчинённых объектов создаются **без префикса**.

В комментарии создаваемого объекта следует указать **номер задачи**, по аналогии с заголовочным комментарием добавляемого кода, но без знаков «++». Это обеспечит привязку объекта конфигурации к задаче, отыскиваемую глобальным поиском.

*Пример*: Создать реквизит «ОценочнаяСтоимость» документа «ЗаказКлиента».

*Действия разработчика*: в конфигурации создается следующий реквизит:

Имя: MD_ОценочнаяСтоимость  
Синоним: Оценочная стоимость  
Комментарий: DT-48

## **4.2** **Добавление подчиненных объектов в объекты, добавленные разработчиком**

Добавляемые подчиненные объекты конфигурации в корневые объекты с префиксом (то есть добавленные разработчмком), **НЕ** должны **снабжаться "префиксами метаданных"**:

Синонимы таких подчинённых объектов создаются **без префикса**.

В комментарии создаваемого объекта следует указать **номер задачи**, по аналогии с заголовочным комментарием добавляемого кода, но без знаков «++». Это обеспечит привязку объекта конфигурации к задаче, отыскиваемую глобальным поиском.

*Пример*: Создать реквизит «ОценочнаяСтоимость» документа «DT_ЗаказКлиента».

*Действия разработчика*: в конфигурации создается следующий реквизит:

Имя: ОценочнаяСтоимость  
Синоним: Оценочная стоимость  
Комментарий: DT-48

## **4.3** **Наследование типовых подчиненных объектов в расширение**

Наследуемые объекты не меняют своего имени (**без префикса**).

В комментарии наследуемого объекта следует указать **номер задачи**, по аналогии с заголовочным комментарием добавляемого кода, но без знаков «++». Это обеспечит привязку объекта конфигурации к задаче, отыскиваемую глобальным поиском.

*Пример*: Унаследовать в расширение реквизит «ОценочнаяСтоимость».

*Действия разработчика*: в конфигурации наследуется реквизит и устанавливается:

- Комментарий: DT-48

# **5. События объектов**

## **5.1 Методы событий объектов "ПередЗаписью","ПриЗаписи", "ПередУдалением"**

При описании методов событий объектов "ПередЗаписью", "ПриЗаписи" и "ПередУдалением" (в том числе в подписках, расширениях и т.д) в обязательном порядке должна быть вставлена конструкция

```
Если Источник.ОбменДанными.Загрузка Тогда
    Возврат;
КонецЕсли;
```

При использовании кода до проверки на ОбменДанными.Загрузка, обоснование этому должно быть описано в комментарии к коду, и добавлен вариант программно не выполнять алгоритм с помощью единой функции для всей конфигурации, например:

```
Функция ПриЗаписи(Источник) Экспорт
    // Програмное свойство для не выполнения операций
    Если Источник.ДополнительныеСвойства.Свойство("DT_ОтключитьЛогикуПриЗаписи") Тогда
        Возврат;
    КонецЕсли;

    //Выполняется перед првоеркой на обмен данными, так как изменение нужно фиксировать всегда
    ЗафиксироватьИзменениеКонтрагента(Источник);

    Если Источник.ОбменДанными.Загрузка Тогда
        Возврат;
    КонецЕсли;

    ...
КонецФункции
```

## **5.2 МодульМенеджера.ОбработкаПолученияДанныхВыбора**

При переопределении этого метода следует учитывать необходимость обработки типовых отборов, переданных через Параметры.Отбор

## **5.3 Ограничение параметров выбора на форме**

При ограничении параметров выбор рекомендуется использовать свойство "ПараметрыВыбора" или "СвязиПараметровВыбора" реквизита или элемента формы. Они позволяют фильтровать данные при выборе из формы, вводе по сроке и выборе по истории.

Если логика ограничения более сложная и этих свойств недостаточно, следует сделать доработки:

- В форме установить параметры выбора с именем несуществующего реквизита, например "Отбор.DT_ТолькоАктивныеЮрЛица"
- В форме выбора обработать переданный отбор ИЛИ переопределить форму выбора в методе модуля менеджера ОбработкаПолученияФормы
- В модуле менеджера объекта выбора обработать отбор в событии ОбработкаПолученияДанныхВыбора

## **5.4 Использование подписок на события**
Не рекомендуется использовать подписки на события, так как это может усложнить отладку и понимание кода.
Использование допустимо в следующих случаях:
- Это общий механизм на большое количество объектов, например првоерка даты запрета изменения
- Выполнение общего алгоритма в расширении для того, чтобы не наследовать объекты из основной конфигурации

# **6. Работа с расширениями**

## 6.1. **Общие правила использования расширений**

1. Метаданные (те объекты, которые влекут за собой изменение БД, для простоты понимания это те объекты, к которым можно обратиться в запросе) - должны добавлять в расширения. Это:
    - В некоторых случаях усложнит разработку (например, во внешних обработках метаданные расширения будут не видны), но позволяет не снимать с поддержки основную конфигурацию 
    - Позволит не снимать с поддержки объекты основной конфигурации
    - В некоторых случаях ускорит разработку так как все изменения в расширении (глобальный поиск, сравнение-объединение, анализ кода...)
Доработки кода/форм также выполняются в расширении, если это возможно и не усложняет поддержку системы.
2. При разработке следует учитывать сложность обновления и принимать меры по его облегчению.
3. Правила комментирования и именования объектов соответствуют текущему регламенту
4. Интерактивное изменение формы не допускается, все изменения нужно делать в коде

## 6.2. **Переопределение процедур**

1. По возможности следует использовать аннотации "&После" или "&Перед" и только их
2. При необходимости изменить метод, следует использовать аннотацию "&ИзменениеИКонтроль" с блоками #Вставка #КонецВставки и #Удаление #КонецУдаления
  ```
  &ИзменениеИКонтроль("MD_ЗаполнитьПоДокументу")
  Процедура MD_ЗаполнитьПоДокументу(ДокументСсылка)
    ...
    #Удаление //++ DT-48
    Док.ДокументОснование = ДокументСсылка;
    #КонецУдаления //-- DT-48

    #Вставка
    //++ DT-48
    Док.ДокументОснование = ДокументСсылка.Основание;
    //-- DT-48
    #КонецВставки

    #Вставка //++ DT-48
    Док.ДокументОснование = ДокументСсылка.Основание;
    #КонецВставки //-- DT-48
    
    ...
  КонецПроцедуры
  ```
3. Аннотацию "&Вместо" допустимо использовать только для:
  1. Полной замены метода, **без копирования типового кода** (с пониманием сложности отловить это при обновлении)
    ```
    &Вместо("РазложитьМассив")
    Процедура MD_РазложитьМассив(Массив)
      //алгоритм
    КонецПроцедуры
    ```
  2.  Выбора метода по условию, с использованием "ПродолжитьВызов(...)"
    ```
    &Вместо("MD_ЗаполнитьПоДокументу")
    Процедура MD_ЗаполнитьПоДокументу(ДокументСсылка)
      Если ТипЗнч(ДокументСсылка) = Тип("ДокументСсылка.MD_МойДокумент") Тогда
        //Алгоритм
      Иначе
        ПродолжитьВызов(ДокументСсылка);
      КонецЕсли;
    КонецПроцедуры
    ```

# 7. Разработка ролей

## **7.1 Общие принципы разработки прав**

- Права должны разрешать действия/доступ, а не запрещать
- Для каждого объекта должна быть создана отдельная роль

- Если открытие элемента справочника требует несколько ролей, которые могут использоваться отдельно (например при открытии документа требуется доступ к справочнику валют) - необходимо разделять эти роли. Собираться они будут в пользовательском режиме в профиле групп доступа.  
- Возможны создание одной роли на несколько связанных объектов, если их использование отдельно не предусмотрено, например документ "Заказ клиента" и регистр "Статусы заказов".

- Если доступ к объекту на чтение и/или редактирование должен выдаваться всем пользователям (например доступ к общей форме, обработке или регистру настроек), то можно расширить роль "MD_БазовыеПрава"
- Если к объекту должен иметь доступ только администратор, добавлять отдельные роли не нужно
- Не нужно давать права на регистры, записи по которым формируются документами, так как проведение документов выполняется в привилегированном режиме
- Не должно быть ролей, кроме стандартных, которые дают доступ к общим правам (Администрирование, ТонкийКлиент...)
- Флаг «Устанавливать права для новых объектов» - только для роли "ПолныеПрава"
- Флаг "Устанавливать права для реквизитов и табличных значений по умолчанию" - всегда включен
- Флаг "Независимые права подчиненных объектов" - в исключительных случаях для разделения доступа к реквизитам. В этом случае флаг "Устанавливать права для реквизитов и табличных значений по умолчанию" может быть снят.
- Ни одна роль не должна давать права на интерактивное удаление объектов

## **7.2 Создание ролей**

В имени и синониме роли префикс должен содержаться только в начале

- **MD_Чтение[ИмяОбъектаСоСклонением]** - Просмотр ссылочных объектов и регистров.  
Пример: MD_ЧтениеТиповПроектов.  
Права: Чтение, Просмотр, Ввод по строке
- **MD_ДобавлениеИзменение[ИмяОбъектаСоСклонением]** - создание и изменение ссылочных объектов и регистров  
Пример: MD_ДобавлениеИзменениеТиповПроектов.  
Права: Чтение, Просмотр, Ввод по строке, Изменение, Редактирование, Добавление, Интерактивное добавление, Интерактивная пометка удаления, Интерактивное снятие пометки удаления  
Права для для документов: + Проведение, Отмена проведения, Интерактивное проведение, Интерактивная отмена проведения, Интерактивное изменение проведенных
- **MD_ПросмотрОтчета[имяОтчета]** - просмотр отчетов  
Пример: MD_ПросмотрОтчетаОстаткиТоваров  
Права: Использование, Просмотр
- **MD_ИспользованиеОбработки[ИмяОбработки]** - использование обработок  
Пример: MD_ИспользованиеОбработкиПечатьОС6  
Права: Использование
- **MD_[ИмяПрава]** - права не связанные с объектами  
Пример: "MD_ПросмотрСуммыДоговора".  
Права: Логика использования роли выполняется в коде

В исключительных случаях может ставиться префикс "**MD_Искл_**", если роль переопределяет поведение других ролей в коде. Синоним роли - "**(MD) (ИСКЛ) ..."**.

В случаях, если при формировании имени по шаблону возникает дубль, в обе роли необходимо добавить префикс метаданных, например **MD_ЧтениеДокументаОФД**

## **7.3 Сценарии доработки ролей**

- **Добавление прав на объекты (типовые и из расширения)**  
Вариант 1 - Создание новых ролей в расширении на просмотр и/или изменение  
Вариант 2 - Расширение роли "MD_БазовыеПрава" для всех пользователей
- **Исключение прав на объекты расширения**  
Не требуется, если права разработаны в соответствии с регламентом
- **Исключение прав на типовые объекты**
  - Приоритетный вариант - Наследование типовой роли в расширение и снятие прав.
  - Альтернативный вариант для запрета изменения (не рекомендуется) - Создание роли в расширении без установленных прав (для корректной отработки РЛС). В коде запретить изменение без этой роли.  
  Роль должна называться по шаблону "MD_Искл_MD_ДобавлениеИзменение[ИмяОбъектаСоСклонением]"

## **7.4 RLS**

- При написании ограничений по RLS следует использовать **режим**:  
  - Производительный для доступа к ссылочным объектам  
  - Производительный или обычный для доступа к регистрам
- При написании шаблонов ограничений нужно указывать комментарии, описывающие номер задачи и логику работы
- Переопределение RLS в ролях, наследуемых из основной конфигурацию в расширение, не работает.  
Необходимо вносить изменения в основную конфигурацию или дублировать роль в расширении. Проверено на платформе 8.3.19.1229

# **8. Разработка HTTP-сервисов**

## 8.1 Названия сервисов

Имя HTTP-сервиса должно быть на латинице, например: MD_InternalIntegrations

Корневой URL должен соответствовать названию HTTP-сервиса, но не обязательно должен содержать префикс, например: InternalIntegrations

Имена шаблонов могут писаться:

- 1 шаблон под 1 метод. Тогда допустимо в шаблоне содержать имя метода, например: GetTask
- 1 шаблон на несколько методов. Тогда в шаблоне не должно быть имени метода в названии, например: Tasks (методы GET и POST)

Имена методов должны соответствовать названию HTTP-метода, например: POST

## 8.2 Логирование сервисов

HTTP-сервисы сложнее в отладке, чем обычный код 1С. Поэтому рекомендуется делать логирование действий в ЖР. Для этого:

- При получении запроса, нужно сгенерировать уникальный идентификатор запроса и записать в ЖР: uid запроса, адрес обращения и тело запроса
- Алгоритм выполнения сервиса нужно выполнять в Попытке-Исключении. В исключении нужно вернуть сообщение об ошибке и записать ошибку в ЖР: uid запроса и текст ошибки.
- При успешном выполнении алгоритма, нужно выполнить записать в ЖР: uid запроса, и структуру возврата алгоритма, преобразованный в строку
- В возвращаемой структуре данных должен содержаться uid, чтобы логи другой системы могли быть сопоставлены с логом в ЖР

При таком подходе, по uid запроса можно будет отследить и всю историю обработки внутри 1С, в том числе время выполнения.

## 8.3 Возврат сервисов

Все методы сервиса всегда должны возвращать заранее определенную структуру данных: uid запроса, признак успешного выполнения и детальный результат.  
Детальный результат может быть различным даже в рамках одного метода.  
Если сервис возвращает массив результатов (например статус обработки каждого документа), то детальный результат должен содержать массив структур, как минимум со свойствами: GUID, Success, ErrorText

# **9. Изменения управляемых форм**

Все изменения управляемых форм должны выполняться в программном коде в модуле формы.  
Если изменение невозможно в коде (например свойство пользовательской видимости), то допустимо интерактивное изменении формы, но в модуле формы обязательно должен быть указан комментарий с выполненными изменениями.

# **10. Работа с хранилищем конфигурации**

Все изменения, помещаемые в хранилище должны сопровождаться комментариями. Шаблон комментария: [ПрефиксНомераЗадачи]-[НомерЗадачи]. Например DT-1234  
Никакой дополнительной информации вносить не нужно.

**На некоторых версиях платформы следующие баг работы с хранилищем:**

- Если происходит изменения в модуле команды объекта, то необходимо так же сделать какие-либо изменения в самом объекте, иначе изменения не помещаются в хранилище.

# **11. При разработке следует предусмотреть**

## **11.1 Разработка настроек**

Если доработка:
- или содержит ссылки на пользовательские элементы
- или включает дополнительный контроль
- или относится только к части данных системы (например толь для 1 организации)

то нужно предусмотреть настройки в пользовательском режиме.

При этом:

1. Следует рассмотреть возможность обойти/отключить новую функциональность.  
Для этого может использоваться специальная роль или константа
2. Настройки желательно хранить в существующих элементах справочников (реквизиты) или в регистрах.  
Рядом с настройкой в пользовательском режиме должен быть знак "?" с описанием настройки  
  
Использование "динамических констант/переменных" (если такая подсистема есть в конфигурации) следует максимально минимизировать, так как их тяжело поддерживать.  
Они используются только для:
  - Включения/выключения функциональности  
  Например, включение использования контроля дублей контрагентов
  - Указания ссылки на единичный элемент, когда есть уверенность, что несколько значений не потребуется (аналог константы или предопределенного элемента). Например, регламентированная валюта
  - Указания массива элементов, когда его администрирование удобно в этом объекте, а не в регистре/справочнике.  
  Например, список пользователей для получения рассылки
  - Настройки интеграции  
  Например, json параметров подключения к сервису по api
3. Код доработки должен корректно обрабатывать ситуации, когда настройки не выполнены, и в общем случае не менять стандартное поведение системы
